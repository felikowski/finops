# 8. TypeORM migrations replace `synchronize`

- **Status:** Accepted
- **Date:** 2026-07-12
- **Related:** ADR-0002, ADR-0004, ADR-0007, issue #10

## Context

The backend ran with `synchronize: true` (`backend/src/app.module.ts`) from the start —
convenient in early local development, but unsafe once the app moves toward managed
Postgres, containers, Kubernetes, or database-per-tenant provisioning (issue #10):
schema changes aren't reviewed as explicit files, startup behavior can silently depend on
whatever schema state already exists, and concurrent replicas could all try to mutate
schema at once.

The immediate trigger was adding a semantic dedup key to `billing_line_items`
(`lineItemKey`, unique NOT NULL) — the kind of change `synchronize` can no longer be
trusted to apply predictably going forward.

## Decision

- `synchronize: false` in `app.module.ts`; `migrations: [.../migrations/*{.ts,.js}]` and
  `migrationsRun: true` added instead — a normal boot applies any pending migration, same
  as `synchronize` used to apply schema changes implicitly, but now from reviewed files.
- **One baseline migration** (`src/migrations/<ts>-Baseline.ts`) captures the entire
  current schema (all three tables) rather than starting the migration history from an
  empty diff. Generated by pointing `migration:generate` at a fresh, empty Postgres —
  not the live dev DB, which already matched the entities and would have produced a
  no-op diff. This makes migrations alone sufficient to build a fresh database
  (verified against an ephemeral Postgres container), satisfying issue #10's acceptance
  criterion.
- On the existing dev database (schema already present via years — well, weeks — of
  `synchronize`), the baseline migration was **not executed** (it would fail on
  `CREATE TABLE` for tables that already exist). Instead: the actual pending delta
  (`lineItemKey`/`insertedAt` columns + unique constraint on `billing_line_items`, safe
  because the table was truncated of its pre-dedup duplicate rows first) was applied
  directly, and the migrations bookkeeping table was seeded with the baseline's
  timestamp/name so TypeORM considers it already applied. This is a one-time bridge
  from `synchronize`-managed schema to migration-managed schema; it does not recur for
  future migrations, which run for real via `migration:run`.
- Two entry points, mirroring the existing `start:dev` / `start:dev:remote` split:
  - `data-source.ts` — synchronous `DataSource` export required by the TypeORM CLI
    (`migration:generate`). Reads plain env vars only; does not support
    `SECRETS_SOURCE=infisical` (that fetch is async, incompatible with the CLI's
    synchronous-export contract). Local-only, by design.
  - `migration-runner.ts` — a plain script (`migration:run` / `migration:revert`, each
    with a `:remote` variant) that awaits `loadRemoteSecrets()` first, so it works
    against both a local DB and a deployed one via Infisical.
- The app still connects as `finops_owner` (DDL rights) for now — **not** switched to
  the least-privilege `finops_app` role. Migrations changed *how* schema changes are
  reviewed and applied, not *who* the running app authenticates as; that role split
  (flagged in `secrets.bootstrap.ts`) is deliberately deferred to its own change.

## Consequences

**Positive**
- Schema changes are reviewed, committed files — not implicit startup side effects.
- A fresh database (new environment, tenant, or CI run) can be brought to the current
  schema by running migrations alone, verified end-to-end against an ephemeral Postgres.
- `migration:generate`/`run`/`revert` are documented, scriptable, and consistent with the
  existing local-vs-Infisical (`:remote`) convention used elsewhere in the backend.

**Negative / trade-offs**
- `migration:generate` only works locally (see above) — new migrations must be authored
  against a local Postgres, then committed and applied elsewhere via `migration:run`.
- The app still runs as `finops_owner`; least-privilege `finops_app` remains a follow-up.
- `migrationsRun: true` means every boot still risks applying an unreviewed-at-runtime
  migration if a bad file reaches `main` — the actual review now happens at PR time
  against the committed migration file, not as a runtime safety net.

**Follow-ups**
- Switch the app's runtime DB role to `finops_app` once CRUD-only access is verified
  sufficient (`secrets.bootstrap.ts` already documents the intended path).
- Future schema changes (e.g. issue #8's tenant model) go through
  `migration:generate` + review, not entity edits alone.
